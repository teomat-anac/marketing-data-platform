# Data sources

Where the project's data comes from, what it looks like, and what its limits are.
For term definitions see [`glossary.md`](glossary.md); for what the product does with the data see [`requirements.md`](requirements.md).

---

## 1. Overview

To know whether a channel pays back you need two kinds of data, from two different systems:

| | **GA4** (web analytics) | **Ad platform** (Google Ads, Meta Ads, …) |
|---|---|---|
| Records | What visitors do on the website | What the company buys in advertising |
| Knows | Visits, product views, cart, purchases, revenue, where each visitor came from | Impressions, clicks, **cost** |
| Doesn't know | What the ads cost | What happens on the site after the click (only partly) |
| **In this project** | **Real**: Google's public sample dataset | **Synthetic**: generated by the pipeline |

ROAS = revenue (from GA4) ÷ cost (from the ad platform). The project's core job is to **join the two by date and channel**.

### One customer, seen by both systems

| Step | Ad platform records | GA4 records |
|---|---|---|
| Sees the ad on Google | 1 impression | — |
| Clicks the ad | 1 click, cost $0.80 | — |
| Lands on the shop | — | 1 session, `source = google`, `medium = cpc` |
| Buys a $25 t-shirt | — | 1 purchase, revenue $25 |

ROAS for this customer = $25 ÷ $0.80 = 31.

## 2. GA4 — real data

### What it is
- **Dataset:** `bigquery-public-data.ga4_obfuscated_sample_ecommerce.events_*`
- **Shop:** Google Merchandise Store (Google-branded merchandise), published by Google as a sample.
- **Period:** 1 Nov 2020 – 31 Jan 2021, including Black Friday and Christmas. The project uses **1 Nov 2020 – 24 Jan 2021** (85 days): purchase recording broke in the last week (D18, §5).
- **Format:** the standard GA4 → BigQuery export. That's the same format a real client gets when linking GA4 to BigQuery, which is why it's a good stand-in.

### Structure
- **One table per day:** `events_20201101`, `events_20201102`, …; `events_*` reads them all, and `_TABLE_SUFFIX` filters by date.
- **One row per event:** `session_start`, `page_view`, `view_item`, `add_to_cart`, `begin_checkout`, `purchase`, …
- **Nested fields** (records and arrays, flattened in the staging layer):
  - `event_params`: key/value list (e.g. `ga_session_id`, `page_location`)
  - `ecommerce`: order totals (e.g. purchase revenue)
  - `items`: products in the event
  - `traffic_source`: source/medium/campaign of the user's **first** visit (see limitations)
- **Main identifiers:** `user_pseudo_id` (a browser/device), `ga_session_id` (inside `event_params`), `event_date`, `event_timestamp`.

### Known limitations
| Limitation | Consequence for the project |
|---|---|
| Some values are **obfuscated** (`<Other>`, `(data deleted)`) | They go to a catch-all channel and are never dropped (FR-3). |
| `traffic_source` describes the user's **first** acquisition, not the current visit | Used only to fill in a first session that has no source of its own (D16). |
| Campaign names are hidden (`<Other>`) | No campaign level in the marts (D15). |
| `transaction_id`s are random 6-digit numbers that can collide, and are missing before about 11 Nov 2020 | The order key includes the user; purchases without an ID still count (D17). |
| Tracking gaps: `add_to_cart` not recorded 1–25 Nov 2020; purchase ID and amount missing on 70% of purchases in 25–31 Jan 2021 | Funnel step marked as not recorded (D20); the data used ends on 24 Jan 2021 (D18). |
| `ga_session_id` alone is not unique | Session key = `user_pseudo_id` + `ga_session_id`. |
| `event_date` is a text field (`YYYYMMDD`) | Converted to a date in staging. |
| Revenue is in **USD** | All money in the project is USD (FR-8). |
| The dataset is stored in the **US** location | The project's BigQuery datasets must also be in `US` to query it. |
| Fields added to the GA4 export after 2021 are missing | Use only fields present in the sample. |
| Historical and fixed: no new data arrives | "Daily refresh" re-processes the same data; it demonstrates the mechanism. |

### How a real client would get it
GA4 has a built-in BigQuery link: once enabled, it writes a new daily table to the client's project. There's no backfill; history starts from the link date. The project would read from that table instead of the public sample.

### Cost note
BigQuery bills by bytes read. Read only the columns you need and always filter dates with `_TABLE_SUFFIX`; never `SELECT *` on the events tables.

## 3. Ad costs — synthetic data

### Why synthetic
No public dataset has real ad costs for the same shop and dates; companies keep ad spend confidential. Public ad datasets from other companies can't be joined meaningfully with this shop's data. So the pipeline **generates** costs, shaped to be consistent with the real GA4 traffic.

### Shape
The same grain and metrics as an ad-platform export: one row per **day × channel × campaign**.

| Column | Meaning |
|---|---|
| `date` | Day of the activity |
| `channel` | Paid channel, using the same names as the channel mapping (e.g. Paid Search) |
| `campaign` | Campaign name |
| `impressions` | Times the ad was shown |
| `clicks` | Clicks on the ad |
| `spend` | Cost in USD |
| `loaded_at` | When the row was written |

A real connector (e.g. the Google Ads BigQuery Data Transfer) uses its own column names and units; for example, Google Ads reports cost in micros. Swapping in a real source means replacing the ingestion step and **one staging model**; everything downstream stays the same.

### Generation rules (clicks × CPC)
For each day in the GA4 period, and only for **paid channels found in the GA4 data** (here Paid Search only, see §5):

1. **Clicks** = real visits brought by ads that day (sessions whose own channel is paid, D16) × a factor slightly above 1. Clicks exceed sessions because some clicks never become a visit.
2. **CPC** (cost per click) = a base value per campaign, with small daily noise.
3. **Spend** = clicks × CPC.
4. **Impressions** = clicks ÷ CTR, with CTR a plausible percentage per campaign.

Consequences:
- Spend follows real traffic, so **ROAS moves with real revenue**: it rises when conversion improves (e.g. Black Friday) and isn't fixed in advance (FR-2).
- A **fixed random seed** makes the output identical on every run, so re-running gives no duplicates and no drift (FR-5).
- The generator needs paid sessions per day, so it runs **after** the GA4 staging step.

Settings (D21): one campaign; click factor 1.05–1.15; CPC $1.00 ± 15%; CTR 3% ± 10%. Details and the expected result (Paid Search ROAS about 0.5) are in §5.

Implementation ([`pipeline/src/mdp_pipeline/`](../pipeline/src/mdp_pipeline/), D41): one campaign, `Search - Generic`; seed `20201101`; each row draws its factors from its own random generator, so a row never changes when other days are added. Result: 85 rows, 13,427 clicks and $13,333.97 of spend, so Paid Search ROAS is 0.47 over the 85 days. Two runs give identical rows (same fingerprint), apart from `loaded_at`.

## 4. How the two sources are joined

- **Keys:** `date` + `channel`. Campaign would also be a key where names match, but this sample hides GA4 campaign names (`<Other>`), so the join is on date + channel only (§5).
- **Channel names** come from one mapping (source/medium → channel) applied to GA4. The synthetic costs use the same names by construction; with a real source, campaign naming (UTM tags) has to be aligned with the ad account.
- **Clicks ≠ sessions:** the two systems never match exactly. ROAS and CPA use GA4 for revenue and purchases and the ad source for cost; we don't try to reconcile clicks with sessions.

Each one runs with a 2 GB byte cap; unless stated otherwise they cover all 92 days. Together they billed about 26 GB, under 3% of the free 1 TiB a month.

| Question | Answer |

| Attribution rule (requirements Q2) | Last non-direct click on sessions, see the decision below |
| Revenue definition: tax, shipping, refunds (requirements Q3) | Product value without tax, before refunds (none recorded), see the decision below |

### Structure (E1, E2)
- **`event_params`** (E1, one week): `ga_session_id` and `ga_session_number` are on every event, always as `int_value`. `source`, `medium` and `campaign` are on about a third of the events (14 event types), so **each visit carries its own source**, not only the user's first one.
- **Value types are not stable:** `value` and `tax` are sometimes `int_value`, sometimes `double_value`; `session_engaged` is string or int. Staging must read both slots with `COALESCE`.
- **Obfuscation:** `gclid` and `dclid` (ad click IDs) exist, but every value slot is null.
- **Events** (E2): 17 event names. Funnel steps: `session_start` 355k → `view_item` 386k → `add_to_cart` 58.5k → `begin_checkout` 38.8k → `purchase` 5,692.
- ⚠️ **`add_to_cart` exists on only 74 of 92 days** (`select_item` on 70, `view_item_list` on 33). Tracking gaps: to handle in the funnel (E10).

### Traffic sources (E3, E4, E4b)
- **First touch** (`traffic_source`, user level, E3): the only paid medium is `google / cpc` (15.5k users), always with campaign `<Other>`. Obfuscated buckets are large: `<Other>` 51k users, `(data deleted)` 17.6k.
- **Per visit** (`event_params`, first non-null value in the session, E4):
  - `google / cpc`: 7,667 sessions, campaign always `<Other>`
  - `Partners / affiliate / Data Share Promo`: 1,320
  - `googleads.g.doubleclick.net / referral` (display ads tagged as referral): 122
  - email newsletters (`Newsletter_* / email`): about 200
  - the shop's own domain as a referral (`shop.googlemerchandisestore.com`): 52k, a self-referral (settled in Q2: ignored)
- **94,553 sessions (about 26%) have no source, medium or campaign** on any event. Almost all have a `session_start`; together they hold **1 order** (E4b). They affect session counts, not sales. Settled in Q2 (see Attribution).
- **The medium changes within a session** in many sessions (e.g. 26.8k of 93k `google / organic`), so the rule that picks the session's channel matters (settled in Q2).

### Decision: Q1, paid channels
- **Paid channels = Paid Search only** (`google / cpc`). The generator creates costs only for it.
- **Marts stay at day × channel**, with no campaign level: GA4 hides the campaign names, so there is nothing to join on (D15). `raw.ad_spend` keeps its `campaign` column so a real ad export fits.
- Every channel gets sessions, orders, revenue and conversion rate; ROAS and CPA exist only for Paid Search.
- **Thin data is expected:** about 4 Paid Search orders a week makes weekly ROAS swing. The commentary must say so when it happens (US-5).

Rejected options:
| Option | Why not |
|---|---|
| Affiliates as a second paid channel | 2 orders in 3 months: ROAS would be noise. Real affiliates are paid a % of sales, which would fix ROAS in advance (against FR-2). |
| Display (doubleclick) | 0 orders |
| Invented campaigns inside Paid Search | The GA4 side would stop being real; ROAS differences would come from our split |
| The UA sample | See above |
| Fully synthetic GA4 events with many channels | Too big for the MVP, and the numbers would show only what we put in. A possible later "demo data" mode. |

### Attribution (E14–E19)
- **Self-referrals.** When visitors move between `googlemerchandisestore.com` and `shop.googlemerchandisestore.com`, GA4 records the shop itself as a referral source. It's the most common source change inside a session (E14: e.g. 17.6k sessions go from `google / organic` to the shop's own domain). Sessions whose first source is the shop's own domain hold **$116k, 32% of revenue** (E15, E16). They carry no acquisition information.
- **Sessions without a source are real visits:** 94% have a `page_view` (typically `first_visit`, `page_view`, `session_start`), and 79% are the user's first session (E4b, E17).
- **`traffic_source` fits first sessions.** On a user's first session, `traffic_source` (first touch) describes that very visit. Where a first session has its own source, the two agree in 85% of cases, and in 99.9% for Paid Search (E18). They disagree mostly because this sample's `traffic_source` has lost Affiliates and Email (obfuscated into other values).
- **Models compared** (E16, E19), Paid Search only:

| Model | Sessions | Orders | Revenue | Problem |
|---|---|---|---|---|
| The visit's own source, no other rules | 7,672 | 48 | $3,147 | Self-referrals take 32% of revenue; 94k sessions have no channel |
| First touch (`traffic_source`) for every visit | 15,618 | 153 | $9,056 | Every later visit gets the user's first channel; a January order is credited to a November click, out of line with daily spend; the field has lost Affiliates and Email and includes $46.5k of self-referral |
| **Chosen: last non-direct click on sessions** | **14,433** | **87** | **$7,073** | — |

### Decision: Q2, attribution
**Session-scoped last non-direct click**, GA4's own rule for session traffic sources (D16):
1. **A session's own source** = the first non-null source/medium among its events, ignoring the shop's own domains (self-referrals).
2. **A user's first session with no own source** takes `traffic_source`.
3. **A Direct session, or one with no source,** inherits the user's most recent earlier non-direct channel within **90 days** (the longest GA4 window; with 92 days of data it barely matters). If there is none, it stays Direct.
4. **An order belongs to the session it happens in;** its revenue goes to that session's channel.
5. **Each session keeps two channels:** `own_channel` (what brought this visit; the cost generator counts Paid Search clicks from it) and `channel` (attributed; used by the marts).

### Orders and revenue (E6–E8)
- **5,692 `purchase` events are not 5,692 orders** (E6, E6b, E6c):

| Case | How many | Revenue | What it is |
|---|---|---|---|
| Same `transaction_id`, same user, day and amount | 311 IDs, about 320 extra events | $21.5k extra | Duplicates: the same order recorded twice, a median of 0.04 s apart |
| Same `transaction_id`, different users, days and amounts | 15 IDs | — | Different orders whose IDs collide: the sample's IDs are random 6-digit numbers, and about 10 collisions are expected by chance among 4,450 orders |
| `transaction_id` is `(not set)` or empty, revenue > 0 | 456 events | $31.8k | Real purchases without an ID: none duplicates an order with an ID, and they have item totals |
| `transaction_id` is `(not set)`, revenue 0, no item revenue | 450 events | $0 (not recorded) | Real purchases whose ID and amount weren't recorded: their sessions went through checkout, and only 9 duplicate an order with an ID (E10c). 240 of them fall in 25–31 Jan. |

- **Revenue** (E7): `purchase_revenue_in_usd` equals the sum of the items (within 0.02% overall), so it excludes tax. Tax is a separate field (`tax_value_in_usd`, $28k on the counted orders). Shipping is never recorded.
- **Refunds** (E7b): not recorded. There are no `refund` events, and the refund fields are always empty.
- **Weekly shape** (E8b, under the rules below): rising through November; Cyber Monday (30 Nov) among the top days ($12k); peak week from 7 Dec (825 orders, $59k); a sharp drop over Christmas; recovery in mid-January.
- **The last week (25–31 Jan) has only 103 orders with an amount**, after 361 the week before. Explained by E10b and E10c: purchase recording broke, and 240 of its 343 purchase events have no ID and no amount. The data used ends on 24 Jan (D18).

### Decision: Q3 and Q4, revenue and orders
**Orders (Q4)** (D17):
1. With an ID: one order per (`transaction_id`, `user_pseudo_id`), keeping the first event. Duplicates are removed, and colliding IDs stay separate orders.
2. Without an ID (`(not set)` or empty): one order per event, unless its session already has a purchase with an ID (then it's a duplicate).
3. Revenue as recorded; an order whose amount wasn't recorded counts with revenue $0. *(A first version dropped purchases without ID and amount as empty events; E10c showed they are real.)*

**Revenue (Q3):** `purchase_revenue_in_usd` of those orders. Tax is excluded (it isn't the shop's money, and ROAS is normally computed without it); shipping isn't recorded. Revenue is before refunds, because the data has none; a real client's refunds would be subtracted on the day of the refund.

**Effect:** on the full sample, the first version of the rule gave 4,922 orders and $340,647 instead of 5,692 purchase events and $362,165 (E8a). Final, over the data range kept (D18): **5,025 orders, 206 of them without a recorded amount, and $335,101** (E20). The per-channel figures above (E11, E16, E19) used rougher rules; the final ones are below.

### Session key, dates and tracking gaps (E9, E10, E10b, E10c)
- Every event has a `ga_session_id`. There are 360,129 sessions but only 349,545 distinct `ga_session_id` values, so the session key must include `user_pseudo_id`.
- 845 sessions cross midnight, and 79 purchases happen on a later day than their session's start. A session and its orders belong to the day the session started.
- **`add_to_cart` gap** (E10): zero on 2–15 and 21–24 Nov 2020, and only partly recorded on 1, 16–20 and 25 Nov (fewer add-to-carts than checkouts), while checkouts and purchases continue normally. Reliable from 26 Nov 2020.
- **Purchase recording** (E10b, E10c): before about 11 Nov 2020, purchases have no `transaction_id` (but do have revenue). Throughout the period, 3–5% of purchases have neither ID nor amount; in 25–31 Jan 2021 it's 240 of 343 (70%). These are real purchases: their sessions went through checkout, and only 9 of 450 sit in a session that already has a purchase with an ID.

### Decisions: data range and funnel gaps
- **Data range: 1 Nov 2020 – 24 Jan 2021, 85 days** (D18). The last week is dropped because most of its purchases have no amount; keeping it would show a false collapse in revenue.
- **Funnel gaps** (D20): `add_to_cart` before 26 Nov 2020 is marked as not recorded (`is_tracked = false`, `sessions` null), not as zero. Known tracking gaps are kept in a small list (a dbt seed), so others can be added.

### Decision: generator settings
Paid Search only, one campaign (D21):

| Setting | Value | Basis |
|---|---|---|
| Clicks | own-source Paid Search sessions × a daily factor in 1.05–1.15 | Some clicks never become a visit |
| CPC | $1.00 × a daily factor in 0.85–1.15 | Public e-commerce search average about $1.16 ([WordStream](https://www.wordstream.com/blog/ws/2016/02/29/google-adwords-industry-benchmarks)) |
| CTR | 3% × a daily factor in 0.9–1.1 | Public e-commerce search average 2.69% (same source) |
| Seed | fixed | Identical output on every run (FR-5) |

Expected over the 85 days: about 13,400 clicks and $13,400 of spend, so **Paid Search ROAS is about 0.5**. That follows from the real data (paid visits convert at 0.6% vs 1.5% site-wide), not from a chosen target. Rejected: a CPC of about $0.25 (ROAS about 2), well below public benchmarks.

### Results in the marts
Built by dbt from the rules above ([`pipeline/dbt/`](../pipeline/dbt/)); every test passes.

- **Sessions and own-source sessions** per channel are exactly the E20 figures (333,787 in total).
- **Orders: 5,030 (+5), revenue $335,469 (+$368)** against E20. All five extra orders come from sessions that started by 24 Jan and purchased after midnight. E20 cut the events at 24 Jan and lost them; the dbt models read beyond the range and keep sessions by start day (D39). Orders without a recorded amount: 206, as in E20.
- **Order IDs:** 643 purchase events carry `(not set)`; none has an empty ID.
- **Paid Search ROAS** changes week by week, from 0.17 to 0.89, and is 0.47 over the 85 days ($6,217 ÷ $13,334).
- **Season:** the best day is Cyber Monday, 30 Nov 2020 ($11,910); the best week starts on 7 Dec ($59.2k, 855 orders); revenue falls over Christmas (about $500–1,200 a day on 24–27 Dec) and recovers in mid-January.
- **Funnel** (sessions over the 85 days): visit 333,787 → view_item 70,833 → add_to_cart 13,488 (recorded from 26 Nov only, D20) → begin_checkout 10,526 → purchase 4,538.
